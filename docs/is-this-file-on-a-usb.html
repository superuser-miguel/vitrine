Is this file on a USB?

Vitrine caches thumbnails so a slow USB drive doesn't re-decode every image on every visit — but to do that it has to know a file lives on removable media. Inside a Flatpak sandbox, where /run/media is invisible and the path you're handed is an opaque doc id, that's a question you're not supposed to be able to answer. One extended attribute answers it cleanly.

July 2026 · GNOME · Flatpak · Rust · portals

This is a companion to What the document portal actually does — that one tours the portal in general; this one is a single, practical question it makes surprisingly hard, and the tidy answer. If you've ever wanted a sandboxed app to treat a slow external drive differently from local disk, this is the missing piece.

1Why a USB needs its own cache

A cache miss on local disk is cheap. A cache miss on a USB is a full re-read over the bus.

Vitrine's thumbnails are keyed by file URI and validated by mtime. That's a fine, boring scheme for local files. But the private thumbnail cache is LRU-pruned, and ordinary local browsing evicts from it constantly. When an evicted thumbnail belongs to a file on a USB drive, regenerating it means reading the whole image back over the bus just to downscale it — the expensive read is the source read, not the decode.

On a fast NVMe you'd never notice. On a 2012 WD My Passport — spinning platter, USB 2, exactly the worst case — you notice every time. So the fix is to give removable media a cache that local browsing can't touch:

  • a separate removable-thumbnails/ directory,
  • with its own budget (8 GB by default) and its own prune,
  • so no amount of local browsing can evict a removable thumbnail.

First visit to a folder on the drive pays the slow decode tax once; every visit after is instant, and it survives unplug/replug. All of which depends on one classification at decode time: is this source on removable media? Get that wrong and the whole tier is pointless.

2The easy 90%: a path heuristic

For an unsandboxed app, the path tells you everything.

Outside a sandbox the answer is right there in the URI. Removable media auto-mounts under a predictable root, and network shares announce themselves in the scheme:

file:///run/media/<user>/<drive-label>/photo.jpg   → removable
smb://server/share/photo.jpg                        → network
sftp://host/path/photo.jpg                          → network
/home/<user>/Pictures/photo.jpg                     → local

A prefix check on /run/media/ plus a short list of network schemes (smb://, sftp://, ftp://, nfs://, mtp://, and friends) is enough for a direct-filesystem app. Vitrine keeps exactly this heuristic as the fast path — and for a native (non-Flatpak) build, it's the whole story.

Then you sandbox the app, and the path stops telling the truth.

3The sandbox is blindfolded

The portal's whole job is to not show you the host path — so the heuristic can't fire.

A Flatpak sandbox has no /run/media. When the user grants a folder on a USB through the file chooser, the document portal re-exports it through a FUSE mount, and every file underneath arrives looking like this:

file:///run/user/<UID>/doc/<opaque-doc-id>/photo.jpg

The real /run/media/… location is hidden behind the doc id — on purpose. That's the portal doing its job: the app gets access to the bytes without being told where on the host they live. Which means both obvious approaches fail:

  • The path heuristic can't fire — there's no /run/media anywhere in that URI, just /run/user/<uid>/doc/….
  • File.find_enclosing_mount() — the thing you reach for first — is useless here. It returns the fuse.portal mount, which is the same for a USB, a network share, and a file in your home folder. It describes the portal, not the drive.
Where the obvious approach dead-ends

find_enclosing_mount() feels like the designed answer — "which mount is this file on?" — and it compiles, runs, and returns something plausible. It just always returns the portal. If you're going to trust it, log what it actually says for a USB file first; it says fuse.portal, every time.

4The one extended attribute

The portal hides the host path from the URI — and hands it back as an xattr.

The document-portal FUSE mount exposes the real host path as an extended attribute on each file. From the shell:

$ getfattr -n user.document-portal.host-path granted-file.jpg
# file: granted-file.jpg
user.document-portal.host-path="/run/media/me/MY-USB/photo.jpg"

There it is — the real location, the one the URI wouldn't give you. From gio the attribute is spelled xattr::document-portal.host-path (gio drops the user. namespace prefix), and the whole resolver is a dozen lines:

fn doc_portal_host_path(file: &gio::File) -> Option<String> {
    let info = file
        .query_info(
            "xattr::document-portal.host-path",
            gio::FileQueryInfoFlags::NONE,
            gio::Cancellable::NONE,
        )
        .ok()?;
    info.attribute_string("xattr::document-portal.host-path")
        .map(|s| s.to_string())
}

So the full classification is a heuristic with a sandbox-aware fallback, and the ordering matters for cost: check the cheap URI heuristic first; only if the URI is a /run/user/<uid>/doc/… path do you pay for the xattr query, and then classify the host path it returns:

fn is_removable_source(file: &gio::File, uri: &str) -> bool {
    if is_removable_uri(uri) {
        return true;                       // /run/media, smb://, … — free
    }
    if is_doc_portal_uri(uri) {            // only doc-portal paths pay for this
        if let Some(host) = doc_portal_host_path(file) {
            return is_removable_path(&host);   // classify the *real* path
        }
    }
    false
}

Ordinary local files never touch the xattr path, so they pay nothing. And the part that actually needed proving — that a sandboxed process can read this attribute at all — checks out: on a real USB, from inside the Flatpak, the query returns the /run/media/… host path and the removable-thumbnails/ cache fills. It works.

There's also a D-Bus route — org.freedesktop.portal.Documents.Info(doc_id) returns the host path too — but the xattr is cheaper: one getxattr on a file you already have open, no round-trip to a service.

Lesson

When a sandbox hides something from the obvious API, check whether it's re-exposed somewhere deliberate. The portal can't put the host path in the URI without defeating itself — but it will hand it to code that asks by name. document-portal.host-path is that name.

5Two /run trees people conflate

They both start with /run and both involve a mount, and that's where the resemblance ends.

The whole confusion comes down to two unrelated paths under /run that are easy to mistake for each other:

PathWhat it is
/run/media/<user>/<label>/…the real removable auto-mount
/run/user/<UID>/doc/<doc-id>/…the document-portal FUSE view

Different base dirs entirely: one under /run/media keyed by username, the other under /run/user keyed by numeric UID with a literal doc segment and an opaque id. The xattr is the bridge from the second back to the first — and only the second kind needs the bridge.

With classification solved, the rest of the feature is plumbing: removable decodes are routed to the removable-thumbnails/ dir with its own budget and prune, reads check it first, and a slow drive is fast on its second visit. The one non-obvious line in the whole thing is the attribute name.

The follow-up: stop keying on the path at all

There's a deeper fix hiding here. Keying the cache by path means a drive that remounts at a different doc id — or a different /run/media label — looks like a fresh drive and re-decodes. Vitrine's next tier keys thumbnails by content hash (BLAKE3) instead, so a thumbnail survives a remount and even dedupes the same photo across two different drives. That's a separate story — but it's the reason the path-based removable tier is a floor, not the ceiling.

Rule of thumb

"Is this file on removable media?" has a free answer for a native app (the path) and a one-xattr answer for a sandboxed one (document-portal.host-path). What it doesn't have is a portable-across-remounts answer — for that you stop asking about location and start asking about content.

The whole trick, in one line

Everything above reduces to this: a sandboxed app can't see /run/media, but it can ask any portal-granted file for xattr::document-portal.host-path and get the real location back. Query it only for /run/user/<uid>/doc/… paths so local files pay nothing, classify the host path it returns, and route removable decodes to a cache local browsing can't evict. Sandboxed apps are supposed not to know host paths — which is exactly what makes "how do I tell this is a USB" a real question, and the host-path xattr the clean answer.
