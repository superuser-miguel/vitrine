Blank cells, warm cache

Fling a folder of thousands hard, let go, and don't touch it — and in Vitrine the whole screen of thumbnails stays blank for a full minute. Not decoding. Blank. The catch: their thumbnails were already decoded, sitting finished in the RAM cache the whole time. This is the same GtkGridView over-bind from last time — back through a different door.

July 2026 · GNOME · Rust · GTK4 · virtualized lists

A quick recap of the machinery, because the whole bug lives in the gap between two parts of it. Vitrine's grid is a virtualized GtkGridView: thousands of photos, a few dozen live cell widgets, recycled as you scroll. When a cell is bound to an image whose thumbnail isn't in the RAM cache, the app journals a load request for that cell into a queue. A debounced flush drains the queue onto a bounded decode worker, centre-of-viewport first.

That queue had a cap. It kept its newest 400 requests and dropped the rest — the kind of bound you add without much thought, so a berserk scroll can't grow an unbounded backlog. It is exactly the wrong bound, and it took a fling, a stopwatch, and one wrong suspect to see why.

1The wrong suspect

The newest code is not the guiltiest code, however much it feels it.

The blank-cell reports arrived days after I'd shipped a new cache tier — a content-hash layer that lets an identical photo reuse one decoded thumbnail across folders and drives. New code, new persistence, new timing. Of course I suspected it. It felt like a caching bug: the cells that stayed blank were exactly the ones a cache was supposed to fill.

Rather than read the new tier's code and talk myself into a story, I ran it as an experiment. Two identical fling sessions on the same folder, one with the content tier on and one with it off, both logging every load completion:

content tier ONcontent tier OFF
load completions532542
failed loads00
blank on-screen bandsame blocksame block

Identical. The new tier changed where a thumbnail came from and changed nothing about the blanks. It had exonerated itself in one A/B, and the bug was older and lower than the code I'd been staring at.

Where I nearly went wrong

I spent the first hour reading the freshest module in the tree because recency reads as guilt. The A/B cost ten minutes and pointed the other way. Suspect the new code if you like — but test the suspicion before you read it line by line, or you'll find a plausible culprit whether or not it's the real one.

2Fifty-four seconds of nothing

The most damning log line is often the one that isn't there.

With the tier cleared, I flung a 7,300-image folder to a dead stop around position 2924 and watched the load log. The debounce fired, a burst of completions scrolled past, and then—nothing. For fifty-four seconds the log was silent: queued=0, zero completions, no decode activity at all, while roughly two rows of thumbnails sat blank in front of me. It only broke when I nudged the scrollbar at the 66-second mark, which bound the cells afresh and painted them instantly.

Silent is the tell. A slow decode logs progress; a stuck worker logs a full queue. This logged an empty queue and idle workers — the app believed it had nothing left to do, in front of a screen with everything left to do. So I looked at which positions the flush actually served, and the numbers were quietly absurd:

# fling stops with the viewport resting on ~2870–2930
VDBG-LOAD pos=2931 src=disk showing=true    # painted...
VDBG-LOAD pos=3050 src=disk showing=true    # ...below the fold
VDBG-LOAD pos=2892 src=content showing=false   # viewport cell — applied to no one
VDBG-LOAD pos=2905 src=content showing=false   # viewport cell — applied to no one

The flush painted about 160 cells at positions 2931–3094 — a full screen's worth, all below the resting viewport, all showing=true. The cells you could actually see, 2870–2930, did get decoded — but every one completed showing=false: finished, dropped into the RAM cache, and applied to no cell. The pixels existed. They just had nowhere to land.

A bound cell that never received its load request is never repainted. Nothing in the pipeline goes back to ask "is there a live cell here that's still blank?" — the request was the only thing that would have told it, and the request was gone.

3The cap that keeps the wrong 400

A virtualized list binds ahead of you — so what you're looking at is the oldest news.

Two facts had to be reconciled. The viewport's own cells were decoded but landed nowhere (their requests were gone), while cells a full screen below got served perfectly. What decides which requests survive to the flush? The cap: keep the newest 400, drop the oldest. So the question became — during a fling, are the viewport's requests the newest or the oldest in that journal?

This is where the last post comes back to collect. That one ended at a 60-line reproducer proving GtkGridView keeps a bind buffer far larger than the viewport — a fixed 32 × columns + 1 live cells, ten-ish times what's on screen. At rest that buffer straddles the viewport. But in motion it sits ahead of you, in the direction of travel: as the fling races toward 2924, GTK is already binding cells at 3050, 3090, well past where you'll stop. Those far-ahead binds happen last, so they are the newest entries in the journal. The rows you're braking to a stop on were bound earlier — they are the oldest.

              journal (capped: keep newest 400, drop oldest)
   oldest ───────────────────────────────────────────── newest
   [ 2870..2930 ]         [ ...settle churn... ]      [ 3050..3094 ]
     the viewport                                       far below the fold
     ▲ dropped off the back                             ▲ kept
     the cells your eyes are on                         the cells no one can see

So "keep the newest 400" is precisely "keep the cells the toolkit bound furthest ahead of the fling, and throw away the ones under the user's eyes." The flush then did exactly as told: it painted the 160 below-the-fold survivors, reached the end of the queue, saw queued=0, and went to sleep. The viewport stayed blank not despite the cap but because of it.

Lesson

Recency is a terrible eviction key for a cell-request queue, because in a virtualized list "recently bound" means "bound ahead of where the user is heading," not "near what the user sees." A newest-N cap on such a queue evicts the viewport first, every time it matters most.

4The queue was drained centre-first — into no one

The completion order told me the requests were gone before the queue was built, not dropped after.

One thing still had to be ruled out: maybe the viewport requests were in the queue and got starved during the drain — outraced by other work rather than evicted before it. The completion order settles it. The decode pump drains centre-out: it serves the request nearest the viewport centre first, then fans outward — the same priority discipline from the last post. If the viewport's requests had been in the queue, they'd have been served first, not never.

They weren't served at all. The centre-most positions produced no completions, showing=true or otherwise — they simply weren't in the queue to drain. Their entries had already fallen off the back of the cap before the flush assembled the queue. The showing=false completions in the log were a separate, sadder thing: cell-less prefetch requests from earlier in the fling, decoding the same positions into the RAM cache, applied to nobody. That's how the paradox held — warm cache, blank screen — the pixels got made by prefetch and had no cell to go to, while the real cells' requests had been thrown away.

That last diagnostic — a per-load probe printing pos, src, and crucially showing — existed only to corner this bug. Once the completion order proved the requests were evicted rather than starved, it had done its job and came back out. It's the smallest kind of instrumentation: one line that answers one question, deleted the moment the question is answered.

Lesson

When work is missing, the order of what did complete tells you whether it was starved or never queued. A centre-first pump that skips the centre isn't losing a race — it never had the entry. That distinction is the difference between tuning the scheduler and fixing the queue.

5The bound is the pool, not a number

A cell-request queue is already bounded — by the number of cells.

The cap was solving a problem the queue doesn't have. There is no unbounded backlog to fear, because there are only ever a few hundred live cells; a request that can't map back to a live cell is worthless anyway. So the fix is to stop counting and start keying. The journal is now deduped per cell — a rebind replaces that cell's entry instead of appending a new one — and the count cap is gone. The queue's size is bounded by the cell pool, which is the only bound that was ever correct. Evicting an on-screen request is now structurally impossible: an on-screen cell is a live cell, and every live cell owns exactly one slot.

// before: append, then trim to the newest 400 — evicts the oldest (== the viewport)
pending.push(LoadRequest { position, cell });
if pending.len() > 400 { pending.drain(0..pending.len() - 400); }

// after: one slot per cell; a rebind refreshes it; no count cap
pending.insert(cell.id(), LoadRequest { position, cell });

Two more things surfaced in the same few lines, both worth naming plainly:

  • A stale centre. The flush computed the viewport centre for its priority ordering after it had already enqueued, so the first drain ranked against the pre-fling centre. Moved the centre update ahead of the enqueue. Small, but it's the difference between fanning out from where you stopped and where you started.
  • A latent RAM miss. At bind time a cell looked up the RAM cache under a key that omitted the edit suffix (orientation + crop) the loader actually stores under — so a rotated or cropped image could never repaint from RAM on bind, only by redecoding. Unrelated to the fling, exposed by staring at the same code path. Fixed.

The same bug, a third time

The grid's filmstrip had the identical disease with a smaller number: FILM_QUEUE_CAP = 96, against a strip that binds ~200 cells. A short drag could bring on screen a cell that had already been bound and then trimmed off the cap — blank, with no path to re-queue it. Same shape, same fix: deduped per cell, cap removed, the bound pool is the bound. This is the third time this class of bug has been fixed in Vitrine — the filmstrip had a first version of it patched back in the spring — which is exactly why it's now written down as an invariant rather than a fix:

Never put a count cap on a queue of cell requests. The toolkit binds far ahead of the viewport, so a count cap always evicts the rows on screen first. Dedup per cell; let the pool be the bound. Count caps are legitimate only for cell-less work — prefetch, background writes — where losing an entry costs a cache warm, never a blank cell.

Lesson

When the same bug shows up a third time in different clothes, the deliverable isn't the third fix — it's the sentence that stops a fourth. "Never count-cap a cell-request queue" now lives in the architecture notes, next to the reproducer that explains why.
